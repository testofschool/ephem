# LinkedIn Phase 3 초안

상태: **새 게시글용 초안, 미게시**. 기존 게시글의 수치 수정과 별도의 문안입니다.
기존 [v0.2 영문 초안](LINKEDIN_DRAFT.md)은 그대로 보존했습니다.

## 기존 글의 2번 항목에 넣을 문단

2. 요청이 끝난 뒤, 검증을 통과한 변경만 반영합니다.

EPHEM Phase 3는 요청마다 새 COW 워커를 만들고, 실행 결과와 상태 변경을
부모 프로세스가 검증한 뒤 한 개의 데이터베이스에 커밋합니다. Linux ARM64에서
측정한 native 워커 생명주기 p95는 약 0.52ms였습니다. PHP HTTP 요청 전체의
p95는 3.316038ms로, 두 수치는 서로 다른 구간을 측정합니다. SQLite 테스트의
다섯 가지 치명적 오류 시나리오에서는 손상된 키가 커밋된 사례가 0건이었고,
각 오류 뒤의 정상 요청도 복구됐습니다. 이 결과는 해당 테스트 범위의 관찰이며,
프로덕션 상태는 HOLD입니다.

## 전체 게시글 초안

요청 하나가 끝나면, 그 요청의 프로세스도 끝내면 어떨까요?

EPHEM은 이 질문에서 시작한 실험용 Linux 런타임입니다.
Phase 3에서는 요청마다 프로세스를 버리는 구조에, 상태 변경을 검증한 뒤
반영하는 경로를 더했습니다.

1. 요청마다 새 워커를 만듭니다.

미리 준비한 프로세스에서 copy-on-write 방식으로 워커를 만듭니다.
워커는 제한된 상태 명령만 전달할 수 있고, 직접 데이터베이스에 접속할
자격 증명이나 새 네트워크 소켓을 받지 않습니다.

2. Linux ARM64에서 native 생명주기 p95 약 0.52ms를 기록했습니다.

워밍업 100회 뒤 1,000개 샘플을 측정한 결과입니다. 정확한 값은 0.520076ms이며,
디스패치·fork·seccomp·상태 왕복·출력 종료·프로세스 회수까지 포함합니다.
시작 비용은 제외했습니다. 이 회차의 PHP HTTP 응답 전체 p95는 별도로 3.316038ms였습니다.

이후 원격 동기화 검증에서는 native p95가 1.444133ms였고, PHP paired delta p95는
3.730803ms로 <2ms 게이트에 실패했습니다. 0.52ms는 보존된 한 회차의 관찰값이며,
안정적인 지연이나 속도 개선을 입증하지 않습니다. 실패 기록도 함께 공개합니다.

3. 오류가 나면 변경과 응답을 보류합니다.

SQLite 테스트에서 SIGSEGV, 금지된 시스템 호출, 비정상 종료, 시간 초과,
검증 거부를 주입했습니다. 다섯 시나리오 모두 HTTP 500을 반환했고,
손상된 키가 커밋된 사례는 0건이었습니다. 각 오류 뒤 정상 요청도 복구됐습니다.

다만 정상 종료 자체가 안전한 계산을 증명하지는 않습니다.
허용된 명령처럼 보이는 조용한 손상은 커밋될 수 있고, 정상 응답으로
읽을 수 있는 비밀을 내보내는 문제도 이 구조만으로 해결되지 않습니다.
여러 저장소를 하나로 묶는 원자적 커밋도 지원하지 않습니다.

그래서 Production: HOLD를 유지했습니다.
이번 재현에서 PostgreSQL과 BPF LSM은 실행하지 않았고,
x86_64 검증과 프로덕션 부하 측정도 남아 있습니다.

숫자와 한계를 함께 공개해야 다음 실험의 출발점이 분명해진다고 생각합니다.
코드와 원시 측정값, 실패 기록을 저장소에 함께 남겼습니다.

https://github.com/testofschool/ephem

Linux 격리나 데이터베이스 커밋 경계를 다루시는 분들께,
이 구조에서 먼저 검증해야 할 실패 시나리오를 듣고 싶습니다.
